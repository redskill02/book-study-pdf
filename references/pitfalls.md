# 실제로 겪은 함정 — 먼저 읽어라

작업을 시작하기 전에 이 문서를 읽으면 같은 실수를 반복하지 않는다.
모두 실제로 발생했던 것이고, 대부분 **되돌리는 데 시간이 크게 들었다.**

## 1. 콘솔 인코딩 착시 — "한글이 깨졌다"는 오판

**증상** — Python `print()`로 한글을 찍었더니 `����`로 보였다. 텍스트 레이어가 깨졌다고 결론 내렸다.

**진실** — 데이터는 멀쩡했다. Bash 도구의 stdout이 **cp949**라서 그렇게 보였을 뿐이다.
사용자가 직접 열어 확인해 지적해줬다.

**규칙** — 한글 결과는 **절대 stdout으로 판단하지 않는다.**
UTF-8 파일로 쓰고 `cat`으로 읽는다.

```python
io.open("out.txt", "w", encoding="utf-8").write(result)
```
```bash
cat out.txt
```

이 오판 때문에 "느린 PNG 렌더링으로 확인하라"는 잘못된 규칙을 한동안 갖고 있었다.
**틀린 전제 위에 세운 규칙은 반드시 함께 폐기한다.**

## 2. `$100M`이 bash 큰따옴표 안에서 확장된다

`"$100M Offers"` → `00M Offers`. `$1`이 위치 인자로 치환된다.

**해결** — 작은따옴표를 쓰거나, Python에서 `glob("*Offers")`로 찾는다.
한글+`$` 경로는 아예 **Python으로 처리**하는 편이 안전하다.

## 3. bash 히어독이 백슬래시를 먹는다

`<<EOF`로 Python 정규식을 넘기면 `\s`, `\(`가 사라져 `unbalanced parenthesis`가 난다.

**해결** — 구분자를 **따옴표로 감싼다**: `<<'PYEOF'`. 또는 Write 도구로 파일을 만든다.

## 16. 원서 자체의 OCR 오류를 그대로 옮긴다

원문에 `43비트의 레지스터가 1개 있으면 모든 주소를 참조할 수 있다`는 문장이 있었다.
그런데 바로 앞에서 주소 범위를 `00000000~FFFFFFFF`로 잡고 있다 — **32비트**가 맞다.
OCR이 `32`를 `43`으로 읽은 것이다.

읽다가 잡았지만 **자동으로는 못 잡는다.** 그래서 규칙으로 둔다.

**문맥으로 검산되는 수치는 반드시 검산한다.**
- 비트 수 ↔ 주소 범위 (`FFFFFFFF` = 32비트)
- 진법 변환 결과 (`00100111` = 39가 맞나)
- 바이트 수 ↔ 자릿수 (`8비트 = 1바이트`)
- 압축률 (`12 ÷ 17 = 70%`가 맞나)

**검산이 안 되는 수치(연도·인명·제품명)는 원문 그대로 쓰고, 의심되면 캡션에 원문 페이지를 밝힌다.**

## 17. 뒤집힌 페이지는 "안 보인다"가 아니라 **"본 것 같다"** 로 온다

거꾸로(180도) 들어간 쪽을 렌더해서 읽어봤다. 결과가 이랬다.

| | 구조 | 본문 내용 |
|---|---|---|
| 정방향 | ✅ | ✅ 제목·6개 문항 전부 정확 |
| 180도 | ✅ 장 번호·상자·**문항이 6개인 것까지** | ❌ **한 글자도 확신 못 함** |

**위험한 건 못 읽는 것 자체가 아니다.** 구조가 멀쩡히 보이니까
"제4장 도입부에 워밍업 퀴즈 6문항이 있다"까지는 맞게 쓰고,
**그 6문항의 내용을 지어낼 수 있다.** 빈 쪽이면 차라리 티가 난다.

**규칙**
- 변환 전에 **0.5단계 `rotate.py scan`을 반드시 돌린다.** 육안 확인에 기대지 마라
- **MinerU가 고쳐줄 거라고 가정하지 마라.** 후보각이 `("0","90","270")`이라
  180도는 검출 자체가 안 된다
- 페이지를 읽다가 **구조는 잡히는데 문장이 어색하면 회전을 의심한다.**
  OCR 오류와 회전은 증상이 다르다 — 회전은 **모든 줄이** 동시에 이상하다

## 18. "판정불가"를 한계라고 부르지 마라 — 대개 버그다

`rotate.py`가 **글자 수가 적은 쪽을 곧바로 `판정불가`로 빼고 2차 검사를 건너뛰고 있었다.**
그런데 **뒤집힌 쪽은 0도에서 글자가 거의 안 읽힌다.** 정확히 잡아야 할 대상이
"글자 없는 빈 쪽"으로 오분류돼 검출망을 통째로 빠져나갔다.

『인생을 운에 맡기지 마라』에서 실제로 터졌다 — **1권 표지와 2권 195쪽**이
멀쩡히 뒤집힌 채 `판정불가` 목록에 앉아 있었다. 썸네일로 눈으로 보고서야 찾았다.

**핵심** — 빈 쪽인지 뒤집힌 쪽인지는 **돌려보기 전에는 구분할 수 없다.**
글자가 없다는 사실 자체가 회전의 증상이다. 그래서 조건이 뒤집혀 있었다.

```python
# 틀림 — 뒤집힌 쪽이 여기로 샌다
if chars < MIN_CHARS: state = "판정불가"
elif ...

# 맞음 — 일단 전부 2차로 보내고, 4방향 전부 글자가 없을 때만 판정불가
if chars < MIN_CHARS or tall > TALL_RATIO or mean < CONF_MIN:
    의심.append(r)
```

**더 중요한 교훈** — 나는 이걸 앞서 사용자에게 *"판정불가 쪽은 판정을 못 합니다"* 라고
**한계로 보고했다.** 한계가 아니라 내가 만든 결함이었다.
**"원래 못 하는 것"으로 분류하기 전에 왜 못 하는지 한 번 더 캐물어라.**
한계라고 이름 붙이는 순간 아무도 고치지 않는다.

## 19. 검사기를 고친 뒤에는 반드시 '알려진 버그'로 재검증한다

## 21. 검사기가 '오탐'을 내는 것도 못 잡는 것만큼 나쁘다

`svgfit` 이 <g> 에서 `font-size` 와 `font-weight` 만 상속하고
`text-anchor` 를 빼먹고 있었다. 그래서 <g text-anchor="middle"> 안의 글자를
전부 왼쪽정렬로 계산했고, **폭의 절반만큼 오른쪽으로 밀려** 멀쩡한 상자가 전부 넘침으로 떴다.

브랜드설계자 1장에서 **10건이 떴는데 9건이 오탐**이었다.

**왜 위험한가** — 못 잡는 것(#19)은 조용히 배포되고, 오탐은 시끄럽다. 그래서 덜 위험해 보인다.
그런데 **오탐이 쌓이면 진짜 1건이 그 속에 묻히고, 결국 검사기를 안 보게 된다.**
실제로 그 10건 안에 **진짜 넘침 1건**(만화 말풍선)이 섞여 있었다.

**규칙**
- 검사기가 여러 건을 뱉으면 **먼저 한 건을 손으로 계산해 검증한다.** 전부 고치기 전에 한다
- 상속 목록을 만들 때는 **계산에 쓰이는 속성 전부**를 넣는다.
  폭 계산에는 font-size·font-weight 뿐 아니라 **정렬 기준(text-anchor)** 도 들어간다
- 이 부류의 버그는 `+N.N pt` 값이 **일정한 규칙**을 보인다.
  넘침이 전부 '글자 폭의 절반'이면 정렬을 의심한다

## 23. 보완분을 '가장 가까운 앵커' 앞에 넣으면 절 안쪽으로 들어간다

## 25. `svgfit` 은 **가로만** 본다 — 만화 칸을 뚫는 것은 대개 세로다

4컷 만화 칸을 `y="16" height="200"` 으로 잡으면 아래 테두리가 **y=216** 이다.
그런데 칸 안 마지막 캡션을 `y="216"~"230"` 에 둔 곳이 있었다.
결과 — **테두리 선이 글자 한가운데를 관통**해서 취소선처럼 보였다.

- 만화 칸의 마지막 캡션은 **칸 바닥에서 최소 8pt 위**에 둔다.
  칸이 `y=16 h=200` 이면 캡션 baseline 은 **208 이하**여야 한다
- 칸을 넘어가는 캡션을 쓸 거라면 칸 높이를 먼저 늘린다.
  `viewBox` 높이도 같이 늘려야 한다 — 안 그러면 이번엔 SVG 밖으로 잘린다
- **검사기가 통과했다고 안심하지 마라.** `svgfit` 이 보는 것은 x축뿐이다.
  y축은 여전히 사람이 봐야 한다 (함정 #9 의 세로판)

**덤으로 배운 것** — 칸 높이를 220 으로 늘리자 그동안 칸 **밖**에 있어서
검사 대상이 아니던 글자들이 칸 **안**으로 들어왔고, 그러자 `svgfit` 이
**가로 넘침 1건을 새로 잡아냈다.** 하나를 고치면 가려져 있던 것이 드러난다.
고친 뒤에는 검사기를 **다시** 돌려야 한다.

## 26. '점수차 24배'가 사실은 '1.03배'였다 — 2위가 아니라 꼴찌와 비교하고 있었다

`rotate.py` 가 회전 방향을 고른 뒤 확신도를 이렇게 계산하고 있었다.

```python
win  = max(sc, key=sc.get)
lose = min(sc, key=sc.get)      # <- 꼴찌
margin = sc[win] / sc[lose]
```

글자가 적은 쪽은 네 방향을 전부 채점한다. 『스토리 설계자』 1권 108쪽이 이랬다.

    {'0': 1.8, '90': 4.3, '180': 43.0, '270': 44.4}

**180과 270이 43.0 대 44.4, 사실상 동전 던지기다.** 그런데 꼴찌 1.8과 견주니
`점수차 24.2배`로 찍혔고, `보류`(1.30배 미만) 문턱에 걸리지도 않았다.
**가장 확신 있는 판정처럼 보이는 자리에 가장 위험한 판정이 앉아 있었다.**

실제로 그 쪽은 180도 뒤집힌 SECRET 11 표지였다. 그대로 `fix` 를 돌렸으면
**멀쩡한 쪽을 90도 눕혀 놓고** 검사기는 "보정 완료"라고 했을 것이다.

**고침** — 2위와 비교한다.

```python
order  = sorted(sc, key=sc.get, reverse=True)
win, second = order[0], order[1]
margin = sc[win] / sc[second]
```

재검증(#19 규칙대로 알려진 건으로) — 108쪽이 `뒤집힘 24.2배` 에서
`보류 1.03배` 로 내려왔다. 5쪽(270도, 40.0배)은 그대로 `뒤집힘` 이었다.
**잡아야 할 것은 계속 잡고, 놓친 것만 새로 걸렸다.**

**규칙**
- 순위를 매겨 1등을 고르는 검사기의 확신도는 **반드시 2위와 견준다.**
  후보가 3개 이상이면 꼴찌와의 비교는 **아무 의미가 없다**
- 후보 개수가 상황에 따라 달라지는 코드(여기서는 2개 축 vs 4방향)를 특히 의심한다.
  후보 2개일 때는 꼴찌 = 2위라서 **버그가 드러나지 않는다.**
  글자가 적은 쪽에서만 터졌던 이유다
- 이건 #21(오탐)의 반대다. #21은 시끄러운 오탐, 이건 **조용한 오판**이다



## 27. 180 과 270 이 매번 붙는다 — OCR 엔진이 옆으로 누운 글자를 스스로 세워 읽는다

『콘텐츠 설계자』 회전 검사에서 **보류 3쪽이 전부 같은 모양**이었다.

```
1권  22쪽   {'0': 7.9, '90': 1.6, '180': 414.4, '270': 406.5}   1.02배
3권  10쪽   {'0': 7.1, '90': 3.3, '180': 315.0, '270': 303.5}   1.04배
3권  48쪽   {'0': 5.4, '90': 3.9, '180': 118.0, '270': 120.0}   1.02배
```

세 번 다 1.02~1.04배면 그건 우연이 아니라 **패턴이고, 패턴은 버그다**(함정 #18과 같은 냄새).

원인은 PaddleOCR 안에 있다. **세로로 긴 박스는 인식 전에 엔진이 자기가 90도 돌린다.**
그래서 옆으로 누운 렌더링도 글자가 거의 그대로 읽히고 점수가 같이 올라간다.
180도 뒤집힌 쪽을 270도로 돌리면 글줄이 세로로 서는데, 엔진이 그걸 다시 눕혀 읽어
**정답과 거의 같은 점수**를 낸다. 90도는 반대로 돌아가 못 읽으니 낮게 나온다 — 그래서 비대칭이다.

**점수로는 못 가른다. 박스 모양으로 갈린다.**

```
3권 48쪽   180도 -> 세로박스 0.00 (글줄이 가로)   <- 정답
           270도 -> 세로박스 1.00 (전부 세로)
```

`measure()` 는 세로박스 비율을 이미 돌려주고 있었는데 2차 판정에서 `_t` 로 버리고 있었다.
**가로 줄이 보이는 후보가 하나라도 있으면 그쪽만 남기고** 순위를 매기도록 고쳤다.

- 고친 뒤 3권 48쪽은 `보류 1.02배` → `뒤집힘 180도 21.9배` 가 됐다. 눈으로 본 것과 같다
- **점수 1등이 270도였다.** 함정 #26(2위와 비교)을 안 고쳤으면 이 책은
  멀쩡한 쪽 3장을 90도 눕힌 채 나갔을 것이다. 두 결함이 겹쳐 있었다
- 교훈: **동점은 '못 고르겠다'가 아니라 '이 신호로는 못 고른다'는 뜻이다.**
  같은 측정에서 이미 나오는 다른 신호를 먼저 찾아라


## 28. 0건을 '이상 없음'으로 출력하는 검사기

『콘텐츠 설계자』에서 만화 칸 아래 테두리를 뚫는 글자를 찾는 검사를 즉석에서 짰다.
결과는 `없음` 이었다. 그런데 **같은 쪽을 렌더해서 보니 뚫려 있었다.**

원인은 정규식 한 글자였다.

```python
re.finditer(u'<text[^>]*\by="([0-9.]+)"', body)   # \b 가 백스페이스(\x08)로 들어갔다
```

라(raw) 문자열이 아닌 곳에 `\b` 를 쓰면 정규식의 단어 경계가 아니라
**백스페이스 문자**가 된다. 그래서 **한 건도 매치되지 않았고**, 매치가 0이니
'넘치는 글자 없음'이 되어 통과했다. 실제로는 2건이 뚫려 있었다(ch02·ch09).

**검사기는 '못 찾음'과 '없음'을 구분해야 한다.**
그래서 검사한 대상 수를 세어 함께 찍고, 0이면 실패로 처리하도록 고쳤다.

```
만화 24편 / 글자 703개 검사      <- 이 줄이 있어야 결과를 믿을 수 있다
```

- `build.py comicfit` 으로 넣었다. 만화 24편/글자 703개를 세고,
  0이면 `'이상 없음'이 아니라 검사기 고장이다` 를 출력하며 종료 코드 1을 낸다
- 고친 뒤 **알려진 결함을 일부러 되돌려** 재검증했다(함정 #19) — 되돌리면 rc=1, 복구하면 rc=0
- 교훈: **통과했다는 말보다 '무엇을 몇 개 검사했는가'를 먼저 봐라.**
  검사 대상이 0인 통과는 통과가 아니다. 함정 #21(오탐도 못 잡는 것만큼 나쁘다)의 반대편이다

## 29. 고아 자모 0개는 '안전'이 아니다 — `probe.py`는 **조합 실패**만 잡는다

『무조건 통하는 카피 법칙』은 원본 레이어 고아 자모가 **0개/만자**였다.
`probe.py` 판정은 `레이어 양호`. 그런데 실제로는 이렇게 읽고 있었다.

```
통하는 -> 토하느     파악 -> 가악     찰나 -> 잘나     꿰뚫는 -> 꿰띃는
```

**자모가 부서지지 않고 멀쩡한 다른 완성형 글자로 바뀌었다.**
그래서 어떤 자모 지표로도 안 잡힌다. 게다가 재OCR 후 자모가 0 -> 4로 **늘어나서**
`--compare`가 **"재OCR이 개선을 못 만들었다"** 고 오판했다.

**고친 것** — 원본 자모율이 2.0 미만이면 `--compare`가
"이 대조로는 판정할 수 없다"고 말하고 **사람이 할 일**을 지시한다.
(알려진 고자모 책으로 재검증 완료 — 47.2 -> 0.2 는 여전히 `재OCR이 유효하다`. 함정 #19)

**규칙**
- 자모율이 0에 가까우면 **원본 레이어를 눈으로 몇 쪽 훑는다.** 오인식 낱말 2~3개를 뽑아둔다
- 재OCR 결과에서 그 낱말이 **몇 번 남았는지 직접 센다** (`잘나` 0회 / `찰나` 3회)
- **자모율은 '무사함'의 증거가 아니라 '한 종류의 사고가 없었다'는 증거일 뿐이다**
- 덤 — MinerU가 뭉갠 낱말은 **원본 레이어를 열어보면 선명한 경우가 있다.**
  `백금/백공 효과`로 두 번 다르게 뭉갠 것이 원본에는 **`백곰 효과`**로 멀쩡히 있었다.
  둘은 서로 다른 방식으로 틀린다 — **모르는 낱말은 지어내지 말고 다른 레이어를 열어라**


## 30. '검사 대상은 많은데 전부 오탐'인 검사기 — #28의 반대편

`audit.py` [A]가 헤딩 **461개**를 훑었다. 검사 대상 0(함정 #28)이 아니다.
그런데 42건이 뜨고 **전부 오탐**이었다.

원인은 MinerU 헤딩이 **띄어쓰기를 잃어버린 상태**라는 것.
`돈은제품이아닌혜택에쓰는것` 같은 덩어리는 내용어 단위 매칭에 걸리지 않는다.

**대상 수만 보고 안심하면 안 된다.** 42건을 다 확인하느라 시간을 쓰거나,
더 나쁘게는 **오탐에 지쳐 검사기를 안 보게 된다**(함정 #21).

**규칙**
- 검사기가 여러 건을 뱉으면 **서너 개를 먼저 확인해 오탐률을 잰다.** 전부 고치기 전에 한다
- 오탐률이 높으면 그 검사기는 **버리고 방법을 바꾼다.**
  이 책에서는 헤딩 대신 **고유명사·수치 549개**로 대조해 진짜 누락 5종을 건졌다
  (가장 무거운 것은 **윈저 효과의 어원 통째**였다)
- **대조 검사기는 노트 쪽 마크업도 걷어내야 한다.**
  `"<b>무료로</b> 자료 다운로드"`를 태그째 비교하니 `무료로자료다운로드`가 **없는 것으로** 나왔다.
  원문 쪽 잡음(띄어쓰기·구두점)만 지우고 끝내면 노트 쪽에서 오탐이 생긴다

| 본문이 말한 것 | 그림에만 있던 것 |
|---|---|
| "장바구니 이탈률 **70.19%**" | **이탈 이유 10가지** — 48% 추가 비용 · 26% 회원가입 · 25% 카드정보 · 22% 과정이 길다&hellip; |
| "파워 워드는 **두 가지 종류**가 있다" | 그 두 갈래가 **무엇인지** (포괄성 / 의외성) |
| (본문 언급 없음) | **글 상자에 넣으면 효과적인 네 가지** |

**카피를 고칠 때 필요한 것은 70.19%가 아니라 "48%가 추가 비용 때문"이다.**
본문만 옮겼다면 **읽을거리는 남고 실행할 것이 빠졌을 것이다.**

**규칙** — 컨택트시트에서 **비율·순위·before/after 수치가 든 그림**에 ⭐⭐⭐를 준다.
본문에 그 수치의 **합계나 대표값만** 있고 **내역이 없으면** 그림이 유일한 출처다.

## 32. 검사기가 "0건"이나 "전부 오탐"을 내면, 검사기부터 의심한다

『설득의 법칙』 한 권에서 **검사기 결함 3건**이 한꺼번에 나왔다.
셋 다 **검사기가 조용히 틀린 값을 내놓고 있었고**, 렌더를 보기 전에는 몰랐다.

| 증상 | 진짜 원인 | 고친 것 |
|---|---|---|
| `svgfit` 이 한 SVG에서 15건을 뱉는데 눈으로 보면 멀쩡하다 | `_text_width` 가 **HTML 엔티티를 안 푼다.** `&lsquo;` 하나가 **6글자**로 계산된다. 따옴표가 많은 대사 한 줄이 **실제 폭의 두 배**로 잡힌다 | 태그를 걷어낸 뒤 `html.unescape` 를 한 번 더 태운다 |
| 만화가 26장인데 `render` 가 **"만화 0장"** | 검출 문자열이 `<title>4컷 만화로 재구성</title>` 인데, **SVG `<title>`은 메타데이터라 렌더된 PDF 텍스트에 절대 나오지 않는다** | **눈에 보이는 캡션**(`4컷으로 옮겨 그림`)도 함께 매칭 |
| 사례 상자의 표가 오른쪽 끝에서 **잘려 나감** | `pre { overflow: hidden }` — **긴 줄을 조용히 자른다.** 오류도 경고도 없다 | 글자 9pt→8.4pt + `white-space: pre-wrap` (넘치면 잘리지 말고 접히게) |

세 번째가 가장 위험하다. **잘린 자리는 텍스트 추출로도 안 잡힌다** — PDF 안에는 글자가 남아 있고
**보이지만 않을 뿐**이기 때문이다. `_verify.txt` 의 자수도 정상으로 나온다.

**규칙**
- 검사기가 **0건**을 내면 "통과"가 아니라 **"검출식이 대상에 안 걸리는 것 아닌가"**를 먼저 본다.
  개수를 **다른 경로로 한 번 더 세어** 대조한다(`render` 의 만화 수 ↔ `stats` 의 만화 수).
- 검사기가 낸 것이 **전부 오탐**이면 임계값을 올리지 말고 **측정식**을 고친다.
- **`overflow: hidden` 을 쓰지 않는다.** 넘치면 잘리게 두지 말고 접히게 한다.

## 33. 역방향 대조는 '대상'을 좁혀야 쓸모가 있다

`audit.py` [A]는 **원문 → 노트** 방향이라 **내가 지어낸 말은 못 잡는다.**
그래서 반대 방향(`audit_kw.py`)을 짜는데, **대상을 잘못 잡으면 통째로 못 쓴다.**

처음에는 노트의 **`<b>` 강조 전체**를 대상으로 삼았다. 결과 —
**413건 중 343건이 "원문에 없음"** 이었고 **전부 오탐**이었다.
걸린 것들이 `Q1 →`, `10개 이상`, `(9장·10장)`, `처음 듣는 사람에게 3문장으로` &mdash;
**전부 내가 쓴 글**이지 원문에 대한 주장이 아니다.

대상을 **"원문의 것이라고 내가 주장한 말"**로 좁히면 된다. 즉 **효과·개념 이름과 수치**뿐이다.
82개로 좁히자 남은 것은 **1건**, 그것도 객관식 **오답 보기**였다.

**규칙**
- 검사 대상은 **명명된 용어 + 수치**로 한정한다. 서술문·문제 번호·합격선·장 상호참조는 넣지 않는다.
- **객관식 오답 보기의 수치는 절대 넣지 않는다.** 원문에 없는 것이 정상이라 반드시 오탐이 된다.
- 원문 쪽에는 **복원한 텍스트(`_holetext.txt` 등)도 합쳐서** 본다. 안 그러면 복원분이 통째로 "없음"이 된다.
- `norm()` 은 **HTML 태그를 먼저 걷어낸다**(함정 #30).

**하필 MinerU가 실패한 쪽에는 글자가 멀쩡히 살아 있는 경우가 많다**(함정 #31의 반대 방향).

**변형** — 삼켜지지는 않았는데 **LaTeX 수식 덩어리로 뭉개진 쪽**도 있다(`$$ A \vert \lesseqqgtr = \sum ... $$`).
증상은 다르지만 **본문이 사라졌다는 점은 같다.** 같은 방법으로 복원한다.

## 함정 #34 — audit_kw.py의 태그 제거가 원문 본문을 삼킨다

`norm()` 안의 `re.sub(r"<[^>]+>", "", s)` 를 **원문 OCR 텍스트에 적용하면 안 된다.**
스캔본 OCR은 영문 서지 정보나 특수기호를 `<` `>` 로 잘못 읽는 일이 흔한데,
그러면 **엉뚱한 `<` 와 한참 뒤의 `>` 사이 실제 본문이 통째로 삭제**된다.

『설득의 심리학 3』에서 실제로 **4,029자**가 삼켜졌고,
그중 344자짜리 한 덩어리에 들어 있던 **'피크엔드 효과'** 가
"원문에서 못 찾음 — 지어냈거나 표기가 다르다"로 떴다.
원문 p72 각주에 멀쩡히 있는 말이었다.

- 태그 제거는 **노트(HTML)에만** 한다 → `norm_html()`
- 원문에는 **구두점·공백만** 지우는 `norm()` 을 쓴다
- `scripts/audit_kw_template.py` 는 이렇게 고쳐 두었다

교훈: 이 검사는 **거짓 경보가 나오면 도구를 먼저 의심**한다.
`grep` 으로 원문에서 직접 찾아보면 5초면 판별된다.

## 함정 #36 — SVG `<text>` 안에 `<b>` / `<i>` / `<u>` 를 쓰면 조용히 깨진다

HTML 본문에서 쓰던 습관대로 SVG 도표 안에서도 `<b>` 를 썼다.

```html
<!-- 틀렸다 -->
<text x="34" y="240" font-size="10">② 프로그램 시작 전에 <b>작고 사소한 자발적 약속</b>을 먼저 받는다.</text>
<!-- 맞다 -->
<text x="34" y="240" font-size="10">② 프로그램 시작 전에 <tspan font-weight="800">작고 사소한 자발적 약속</tspan>을 먼저 받는다.</text>
```

`<b>` 는 SVG 요소가 아니라서 렌더러가 **그 부분만 상자 밖으로 뱉어낸다.**
설득의 심리학 4의 라이선싱 도표에서 굵은 부분이 상자 아래 한가운데에
따로 떨어져 찍혔다. **`svgfit` 도 `linegap` 도 잡지 못한다** — 둘 다 태그를 지우고
글자만 재기 때문에, 정작 자리를 벗어난 그 조각은 계산에서 사라진다.

**렌더 이미지를 눈으로 보기 전까지는 알 수 없다.** 4권 전체에서 16곳이었다.

집필 뒤 이 한 줄을 먼저 돌린다:

```bash
grep -n "^<text.*<[biu]>" ch*.html _front.html
```

일괄 치환:
```python
ln.replace("<b>", '<tspan font-weight="800">').replace("</b>", "</tspan>")
```

`<figcaption>` · `.key` · `.kr-case` 안에서는 `<b>` 가 맞다. **SVG 안에서만 금지다.**

## 함정 #38 — 상자 아래로 잘리는 글자는 아무 검사기도 안 본다

`svgfit` 은 **좌우** 넘침을, `linegap` 은 **세로 겹침**을 본다.
그런데 `rect` 의 바닥에 baseline 이 붙어 **받침과 descender 가 테두리에 잘리는** 경우는
둘 다 통과시킨다.

```html
<rect x="20" y="170" width="650" height="72" .../>   <!-- 바닥 = 242 -->
<text x="34" y="240" font-size="10">…</text>          <!-- 여유 2pt — 잘린다 -->
```

네 권을 한꺼번에 재보니 **41건**이었다. 그중 6건은 baseline 이 아예 상자 **밖**이었다
(여유 −10pt 짜리도 있었다). 1·2권은 그 상태로 배포돼 있었다.

**기준 — 마지막 줄의 baseline 은 rect 바닥에서 최소 `font-size × 0.38` 만큼 띄운다.**
(10pt 글자면 4pt. 한글은 받침이 있어 라틴 문자보다 아래로 더 내려간다.)

`scripts/fixbottom.py` 가 찾아서 **rect 높이를 키우는 방향으로만** 고친다 —
글자를 옮기지 않으므로 다른 줄과의 간격이 틀어지지 않고,
아래 rect 와 부딪히면 손대지 않고 `SKIP` 으로 보고한다.

```bash
python "$SKILL/scripts/fixbottom.py" <작업폴더> [<작업폴더> ...]
cat _fixbottom.txt
```

고친 뒤 `svgfit` · `linegap` · `comicfit` 을 다시 돌린다(rect 가 커지면 셋 다 영향을 받는다).

## 함정 #40 — svgfit 지적사항을 손으로 고치려다 문자열이 계속 빗나간다

`svgfit` 이 알려주는 것은 **글자의 앞부분**뿐이다. 그걸로 원본을 찾아 바꾸려면
`<b>` 가 `<tspan>` 으로 이미 바뀌었는지, `&mdash;` 인지 `—` 인지,
`&lsquo;` 인지 `'` 인지를 전부 맞춰야 한다.
설득의 심리학 5 ch06 에서 **같은 편집을 세 번 연속 실패**했다 —
한 번은 `&mdash;` 대신 `—` 를 쓴 줄 때문이었고,
한 번은 `fixbottom.py` 가 이미 rect 높이를 바꿔놓은 뒤였기 때문이다.

**`scripts/autofit.py` 를 쓴다.** 이것은 문자열이 아니라 **좌표**로 `<text>` 를 찾아
`font-size` 만 줄인다. rect 도 y 도 건드리지 않으므로 레이아웃이 틀어지지 않는다.

```bash
python build.py svgfit ; python build.py linegap
python "$SKILL/scripts/autofit.py" .
python build.py svgfit ; python build.py linegap   # 다시 확인
```

ch06 에서 **24건 중 22건이 한 번에 해소**됐고, 남은 2건만 손으로 고쳤다.

계속 남는 것은 **글자 자체가 너무 긴 것**이니 그때 문장을 줄이거나 줄을 나눈다.

세 도구의 역할이 겹치지 않는다:
- `svgfit`/`linegap`/`comicfit` — **찾는다**
- `autofit.py` — 글자를 줄여 **가로 넘침과 줄 겹침**을 없앤다
- `fixbottom.py` — rect 를 키워 **바닥 잘림**을 없앤다

## 42. `autofit.py` 가 지적사항의 절반을 조용히 흘려보내고 있었다

`autofit.py` 는 **앞 12글자 문자열 비교**로 대상을 찾았기 때문에,
지적된 문장에 `—`·`‘’`·`“”` 가 하나라도 있으면 **통째로 빗나갔다.**

(같은 이유로 `<tspan>` 이 든 줄도 못 잡았다.)

**고쳤다** — `unescape` 로 양쪽을 풀고 문장부호·공백을 지운 뒤 비교한다.

```python
def norm(s):
    s = unescape(strip_tags(s))
    return re.sub(r"[\s‘’“”–—'\"·.,!?()\[\]{}<>:;…\-]+", "", s)
...
nbody = norm(body)
for over, frag in hits:
    key = norm(frag)
    if key and nbody and (key[:10] in nbody or nbody[:10] in key):
```

고친 뒤 ch07·ch09 는 **한 번도 손대지 않고 자동으로 전부 해소**됐다.

> 교훈은 함정 #34·#40 과 같다 — **자동 수정이 &lsquo;0건 고침&rsquo; 을 뱉으면
> 내 원고가 아니라 도구를 먼저 의심한다.**
> 특히 `MIN_FS`(7.0) 에 걸려 못 줄이는 경우와,
> 매칭 실패로 아예 손을 못 댄 경우는 **출력이 똑같아서 구분이 안 된다.**
> `_autofit.txt` 의 &lsquo;총 N개&rsquo; 와 `_svgfit.txt` 의 넘침 건수를 **나란히 놓고 봐라.**

## 45. `autofit.py` 가 줄여야 할 양의 절반만 줄이고 있었다 (폭 모델 불일치)

```
1회차: +4.1pt 넘침  →  autofit 이 "고쳤다" 고 보고
2회차: +6.0pt 넘침  ←  숫자가 오히려 커진다
```

글자를 줄이긴 줄였는데 **모자라게 줄여서** 다음 회차에 다시 걸리고,
그 사이 폭 계산 기준이 달라져 넘침 수치가 들쭉날쭉해진다.
(『마케팅 설계자』 ch01 에서 세 번을 돌려도 같은 3건이 계속 남았다.)

**고쳤다** &mdash; `autofit.py` 에 `build.py` 와 **똑같은 `text_width()`** 를 넣고,
`font-weight` 도 읽어 굵은 글씨 계수(1.05)까지 맞췄다.

> 교훈 &mdash; **자동 수정 도구는 검사 도구와 &lsquo;같은 자&rsquo;를 써야 한다.**
> 자가 다르면 도구는 매번 조금씩 모자라게 고치고, 그때마다 &lsquo;고쳤다&rsquo;고 보고한다.

그러고도 남으면 그건 도구 문제가 아니다 &mdash;
**만화 칸(폭 132)에 한글 20자를 7pt 로 넣으면 물리적으로 안 들어간다.**
그때는 `MIN_FS`(7.0) 에 걸려 멈추므로 **문장을 줄여야 한다.**

## 50. Chrome 헤드리스가 답안 뒷부분을 **통째로 삭제**했다

### 규칙 — 빈 페이지가 뜨면 "쪽 수"가 아니라 "내용"을 확인한다

```bash

io.open('_pg.txt','w',encoding='utf-8').write( \
'\n'.join('%2d | %4d | %s'%(i,len(p.get_text().strip()), \
p.get_text().strip().replace('\n',' ')[:70]) for i,p in enumerate(d,1)))"
cat _pg.txt
```

`0 chars` 인 쪽 **앞뒤 쪽의 내용이 이어지는지** 본다.
ch05 는 17쪽이 Q17 중간에서 끊기고 19쪽이 튜터로 넘어가 있었다 — 그 사이가 통째로 없었다.

```python
k = '<div class="a"><b>Q18 &rarr;'      # 답안의 절반쯤 되는 지점
t = t.replace(k, '<div style="page-break-before:always;height:0"></div>\n' + k, 1)
```

`autofit`·`fixbottom` 으로는 안 고쳐진다. 레이아웃이 아니라 **페이지네이션** 문제다.
문항이 **22개를 넘으면** 답안이 세 쪽을 넘길 가능성이 크니 미리 넣어 두는 편이 낫다.

### 그리고 — 모든 챕터에서 한 번에 확인한다

```bash
python -c "
import fitz,io,glob,os
for f in sorted(glob.glob('pdf/ch*.pdf')):
    d=fitz.open(f); t=''.join(p.get_text() for p in d)
    io.open('_chk.txt','a',encoding='utf-8').write('%s | cut=%s | tutor=%s | %dp\n'%(
        os.path.basename(f),'몇 개 맞았나요' in t,'복사해 아무 AI' in t,d.page_count))"
cat _chk.txt
```

**각 챕터의 마지막 블록(합격선·튜터)이 PDF 에 실제로 들어갔는지**를 본다.
`False` 가 하나라도 있으면 그 챕터는 내용이 잘린 것이다.

역방향 대조 스크립트의 키워드 목록은 **템플릿을 만들 때 쓰던 다른 책의 것**이다.
『마인드해킹』에서 그대로 돌렸더니 이렇게 나왔다.

```
검사 대상 82개
노트에 실제로 쓰인 것 9개
   원문에 전부 있다
```

**통과처럼 보이지만, 이 책과 아무 상관 없는 항목 82개 중
우연히 겹친 9개만 본 것**이다. 정작 검사해야 할
연구자 이름 118개 · 편향 41개 · 수치 43묶음은 **한 번도 확인되지 않았다.**

역방향 대조는 **지어낸 인용·수치를 잡는 유일한 장치**다
(『사람의 마음을 움직이는 스토리』에서 날조된 인용 2건을 이걸로 잡았다).
그게 헛돌면 **거짓 안전감만 남는다.**

### 반드시 이렇게 한다

1. 경로부터 고친다 — 템플릿은 `out/src/ocr/*.md` 로 고정돼 있다.
   ```bash
   sed -i 's|os.path.join(W, "out", "src", "ocr", "\*.md")|os.path.join(W, "_srcall", "*.md")|' audit_kw.py
   ```
2. **`ITEMS` 목록을 그 책 것으로 새로 쓴다.** 세 종류를 빠짐없이 넣는다.
   - **연구자·인물 이름 전부** (노트에 이름을 적었다면 검사 대상이다)
   - **편향·효과 이름 전부**
   - **소수점이 있는 수치 전부** (`5.84`, `4.11`, `13.90` — 이런 건 지어내기 가장 쉽다)
3. 각 항목은 `(표시명, [원문 후보들])` 형태로 쓴다.
   **OCR 이 이름을 깨뜨리므로 후보를 여러 개** 준다
   (`셰어`/`세어`, `번벅`/`번바크`, `풀스턴`/`풀레스턴`, `트레하른`/`트러헌`).
4. 판정 전에 공백·가운뎃점·마침표를 **다 지우고 비교**한다.
   원문은 `5,127개` 를 `5127` 로, `40.5` 를 `4 0.5` 로 흘려 놓는다.

**검사 대상 개수가 노트 규모에 비해 터무니없이 적으면 그건 통과가 아니라 미실행이다.**
(마인드해킹: 202개 검사 → 202개 전부 원문 확인.)

## 52. 얇은 강조 바(`height="8~12"`)는 **검사기가 못 잡고 렌더에서만 보인다**

도표 맨 아래 `#eef7f0` 강조 바를 높이 8~12 로 만들면
`svgfit`(가로 넘침)과 `linegap`(세로 겹침) **둘 다 통과한다.**
글자가 가로로도 안 넘치고, 위아래로 겹치는 다른 `<text>` 도 없기 때문이다.

그런데 렌더해 보면 **글자가 상자 위아래 테두리를 뚫고 나온다.**
`font-size="7.4"` 글자는 위아래 여백까지 **최소 14pt** 가 필요하다.

이번 권에서만 5건이 나왔다(ch04 · ch07 · ch08 ×2 · ch99 ×2).

### 규칙

- **강조 바 높이는 `글자 크기 + 7` 이상.** 7.4pt 글자면 `height="16"`.
- 바로 위 행이 `y=234 height=17` 로 끝나면(=251) **바는 254 부터** 시작한다.
  높이를 키운 만큼 **`viewBox` 높이도 같이 키운다.**
- 그리고 **렌더 이미지를 반드시 눈으로 본다.** 이 유형은 검사기로 못 잡는다.

```python
# 얇은 바 일괄 점검
grep -n 'height="\([0-9]\|1[0-2]\)" rx="[0-9]" fill="#eef7f0"' ch*.html
```

## #56 `linegap`의 ‘간격 0.0’은 절반이 오탐이다 — `svgfit`과 함께 읽어야 판별된다

`linegap`은 **같은 y를 가진 텍스트끼리** 겹침으로 본다.
그런데 세 칸 표는 **원래 같은 y에 세 개가 나란히** 놓인다 — 전부 오탐이다.

판별법:
- `linegap`만 뜨고 `svgfit`은 조용하다 → **오탐.** y를 2~3px만 어긋내면 사라진다.
- **둘 다 뜬다** → 진짜 넘침이다. 글자를 줄이거나 두 줄로 쪼갠다.

두 검사를 따로 읽으면 오탐을 고치느라 멀쩡한 도표의 y를 흔들게 된다.
`_svgfit.txt`와 `_linegap.txt`는 **항상 같이 열어라.**

## #60 — `viewBox` 높이를 1px만 넘겨도 표 마지막 행이 통째로 잘린다

『장문정의 마케털이』 2장의 9행짜리 `전략적 네이밍` 표에서 실제로 겪었다.

```
<svg viewBox="0 0 690 300">
  ...
  <rect x="8" y="277" width="140" height="24" .../>   <- 바닥 301
```

**7개 검사기가 전부 통과했다.** `svgfit`은 가로만 보고, `linegap`은 세로 간격만 보고,
`comicfit`은 만화 칸의 `y=236` 테두리만 본다. **세로 방향으로 viewBox를 넘는 것은 아무도 안 본다.**
렌더 PNG를 열어 보고서야 마지막 행의 아래 테두리가 사라진 것을 발견했다.

한 권에서 3건 나왔다 — 300/301, 196/204, 244/247.
**표를 그리다 행을 추가하면 viewBox를 같이 늘리는 것을 잊는다.** 매번 잊는다.

검사는 10줄이면 된다. 챕터를 쓸 때마다 돌린다:

```python
import io,glob,re
for f in sorted(glob.glob('*.html')):
    t=io.open(f,encoding='utf-8').read()
    for m in re.finditer(r'<svg viewBox="0 0 (\d+) (\d+)"(.*?)</svg>', t, re.S):
        H,body=int(m.group(2)),m.group(3)
        mx=0
        for r in re.finditer(r'<rect[^>]*y="([0-9.]+)"[^>]*height="([0-9.]+)"',body):
            mx=max(mx,float(r.group(1))+float(r.group(2)))
        for r in re.finditer(r'<text[^>]*\sy="([0-9.]+)"',body):
            mx=max(mx,float(r.group(1))+2)      # baseline 아래 여유
        if mx>H: print('%s H=%d bottom=%.0f'%(f,H,mx))
```

**교훈** — `svgfit`이 OK라고 세로도 OK인 것이 아니다.
`render`로 눈으로 보는 단계를 건너뛰면 이건 절대 안 잡힌다.

## #94 `s.replace(old, new)` 에서 `old` 가 빈 문자열이면 파일이 수십 MB 로 폭발한다

## #97 `<pre>` 표의 열 정렬은 손으로 맞추지 말고 east_asian_width 패딩으로 생성한다

## #112 `_tbl.table` 셀은 HTML 이스케이프를 하지 않는다 — 코드가 든 셀은 `&lt;` `&gt;` `&quot;`로 직접 쓴다
